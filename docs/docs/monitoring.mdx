Towbar exposes several kinds of health. Read the relevant check and its timestamp before deciding whether an installation or workload is ready.

Start with [Operate Towbar](/docs/operate/index) for an investigation path. Use [System and workload health](/docs/operate/health) for fresh checks, [Performance history](/docs/operate/performance) for Scout measurements, and [Investigate incidents](/docs/operate/incidents) for alert context and delivery outcomes.

## Navigate monitoring

The workspace **Monitor** section contains **Logs**, **Incidents**, and **Vulnerabilities**. [Centralized logs](/docs/operate/centralized-logs) searches retained container output in an optional external ClickHouse database. Workload **Runtime Logs** continues to fetch current container output on demand. On Incidents, choose **Active** or **Resolved**, then optionally filter by severity. On mobile, open **Page menu** for these controls.

## Performance history

Open a server, service, or datastore and select **Monitor → Performance**. Use the time range and chart controls to inspect CPU, memory, disk, and network measurements. Workload views also offer environment and container selection. The URL retains the chart filters, so a shared link opens the same view.

Deployment, container restart, host restart, and hardware change markers connect changes in usage to operational events. Drag across a chart to zoom, or choose a custom time range. Missing measurements appear as gaps. See [Scout Agent](/docs/scout) for collection and retention, and [Deployment comparisons](/docs/deployment-comparisons) for comparing releases over equal windows.

## Alerts, incidents, and vulnerabilities

Use workspace **Incidents** to review active or resolved conditions across every server, service, and datastore. Filter the list by severity. Configure and inspect alert rules from the relevant entity page; [Scout Alerts](/docs/scout-alerts) covers rules and notification destinations. **Vulnerabilities** provides a separate view of known package findings from Service image scans; see [Vulnerability scanning](/docs/vulnerability-scanning).

## System health

Open **Manage → System health** to see the latest control-plane checks, their observation times, and the running version. Towbar checks Temporal at startup and every five minutes. Choose **Run checks** when you need a fresh result immediately. A check marked stale is older than 15 minutes.

The **Towbar version** row shows the installed release and the last time Towbar
checked for an update. A newer stable release gets a yellow **Update available**
label. If your operator has enabled in-app upgrades, choose **Review upgrade**
to check readiness and start the update. Progress and the final result appear
in the same modal. See [Upgrades and recovery](/docs/self-hosting/upgrades#upgrade-from-system-health)
for setup, backups, and help if an upgrade fails.

### Database storage

**Database storage** stacks three parts of Towbar's control-plane PostgreSQL tables and indexes: **Towbar Data** for the platform's other records, **Monitoring Data** for Scout Agent measurements and alerts, and **Analytics Data** for service traffic and browser analytics. A dedicated Temporal workflow records their sizes every two hours and keeps 90 days of readings. The chart plots the latest reading from each day. Older readings made before the Analytics split include Analytics Data in Monitoring Data; their Analytics series is unavailable. The total excludes PostgreSQL system overhead, Temporal's database, backups, and data stored on workload servers. **Run checks** refreshes the control-plane checks; it does not take an extra storage reading.

| Section       | Checks                                     | What to investigate                                                                 |
| ------------- | ------------------------------------------ | ----------------------------------------------------------------------------------- |
| Control plane | API/database, Temporal, worker/maintenance | API reachability, workflow admission, recent worker activity, and version alignment |

## Server and workload health

The server's Checks view records connectivity and runtime observations. Its Services and Datastores sidebar items separate the workloads assigned to the host. Health indicators and tooltips identify healthy, unhealthy, starting, and unavailable observations.

A deployment can succeed and later become unhealthy. Check the latest runtime state and logs instead of relying only on deployment history.

## Allocated CPU and memory

Allocation is the limit declared for a workload. Usage is the latest observed consumption relative to that allocation. CPU percentages account for the number of allocated CPUs; memory percentages use the configured memory limit.

On **Servers → All servers**, the CPU and memory capacity columns describe each host's maximum capacity, not a workload's allocation. When Scout has measured usage, each capacity has a **% used** line below it; hover or focus that line to see when the sample was recorded. These columns are also available on mobile through the horizontally scrollable table. Missing measurements display as **Not measured**, rather than zero.

## Follow an operation

Deployment, preparation, backup, and restore histories show stage progress and final results. Durations update while an operation is running. Date columns show relative time first, with the local date and time below it as **15:26, 10 Sept 2026**. Hover or focus the timestamp to see its timezone.

For runtime problems, inspect the workload's logs and latest health check. For control-plane problems, start with:

```bash
sudo towbar status
sudo towbar logs api worker temporal
```

Configure [notifications](/docs/integrations/notifications) for events that need attention. Use [Troubleshooting](/docs/troubleshooting) to narrow down common symptoms.

## Scout Agent

[Scout Agent](/docs/scout) adds continuous performance history for servers, services, and datastores. Install it from **Server → Settings → Scout Agent** to receive updates every 30 seconds and keep up to 60 days of history. Read the [Scout Agent guide](/docs/scout) for installation, charts, retention, and troubleshooting.
