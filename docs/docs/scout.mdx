## Install Scout Agent

Open a server, choose **Settings → Scout Agent**, select a retention period, and acknowledge installation. Choose **Install Scout Agent**. The server must already be prepared, with its SSH credential and a trusted host key configured.

Scout Agent runs as two small systemd services: a local collector and an HTTPS sender. Both start after a reboot and restart after a crash. The collector reads host counters and Towbar-labelled Docker containers every **30 seconds**. The sender reports to your own Towbar API; it does not open an inbound port on the server.

**Installing** means the worker is setting up the services. **Awaiting report** means installation completed but no sample has arrived yet. **Online** requires a received sample. **No recent report** appears when the latest collection is older than 90 seconds; old data is never presented as a fresh zero.

## Performance history

Open **Monitor → Performance** on a server, service, or datastore. Host charts show CPU, memory, disk, network, and uptime; workload charts show container usage, limits, restarts, and health.

Select the range, environment, instance, and Average or Peak aggregation. Drag to zoom or use **Custom range** for a fixed window. Missing measurements remain gaps. Deployment, restart, and hardware markers help correlate changes.

The Servers list shows recent CPU and memory trends. These are observations, not alert rules. Use [Performance history](/docs/operate/performance) for chart interpretation and [Scout Alerts](/docs/scout-alerts) to configure notification thresholds.

## Alerts and deployment comparisons

Use **Monitor → Alerts** to configure metric rules and public HTTP checks. [Scout Alerts](/docs/scout-alerts) covers thresholds, automatic recovery notifications, enablement, and incident history.

On a service or datastore, **Compare deployments** aligns equal periods after two releases became ready. [Deployment comparisons](/docs/deployment-comparisons) explains sensitivity, sample coverage, and the limits of inferring a regression.

## Retention and resource limits

Retention defaults to **15 days**. Choose 7, 15, 30, or 60 days per server. Raw 30-second samples are kept for 24 hours, then compacted into one-minute summaries. The maintenance worker compacts and expires records in bounded batches. Reducing retention expires older history permanently; increasing it cannot recover expired data.

The collector has a 128 MiB memory ceiling; the sender has 256 MiB for its local geolocation database. Each service has a CPU quota of 5% of one CPU. The retry buffer holds at most **10 MiB or one hour**, whichever is reached first. Oldest samples are dropped when the buffer fills, and diagnostics report dropped samples. The services share a separate volatile journal capped at 8 MiB. A backend outage does not accumulate logs or metrics indefinitely.

Collection is limited to 512 Towbar-labelled containers per server, four concurrent Docker reads, and a 20-second collection deadline. Unavailable measurements are omitted and reported in diagnostics. The agent does not store or transmit application environment variables, secrets, or log contents.

## Credentials and connectivity

The worker installs a dedicated credential scoped to one server. It only authorizes metric ingestion and cannot call the control-plane API or MCP. Updates rotate this credential. The collector and sender use separate service accounts; only the sender reads the upload configuration. Docker access is privileged, so only enable the agent on a server you trust.

The configured `installation.apiBaseUrl` must be an HTTPS URL reachable from the server. The agent validates the certificate and never follows redirects with its credential. Ensure outbound DNS and HTTPS are available. Monitoring uploads have separate limits from API/MCP traffic: 120 requests per server per minute and 600 per originating IP per minute, including buffered catch-up traffic.

## Update, uninstall, and remove a server

Choose **Update Scout Agent** to install the version bundled with the current Towbar worker. Reporting may pause briefly while services restart.

**Uninstall Scout Agent** immediately revokes the upload credential, then stops the services and removes the binary, configuration, and retry buffer. Existing history follows its retention period. A failed uninstall keeps SSH credentials available for retry.

Removing a server revokes its monitoring access and stops future collection in Towbar. Active operations must finish first. The machine, running services, and Docker data remain on the host. Follow [server removal](/docs/servers#remove-a-server) to review the effects on assigned workloads.

## Troubleshooting

Check the agent status and last sample time in **Scout Agent**. On the server:

```bash
sudo systemctl status towbar-monitoring-collector towbar-monitoring
sudo journalctl --namespace=towbar-monitoring --since '10 minutes ago'
```

Do not share `/etc/towbar-monitoring/config.json`; it contains the upload credential. If credentials were revoked, update or reinstall the agent from Towbar. For missing container metrics, verify Docker is running and the containers retain their Towbar ownership labels.

## API and MCP

Use the normal API key authentication for management and history:

| Action            | Route                                                          |
| ----------------- | -------------------------------------------------------------- |
| Agent status      | `GET /v1/api/servers/{serverId}/monitoring`                    |
| Retention         | `PATCH /v1/api/servers/{serverId}/monitoring`                  |
| Install or update | `POST /v1/api/servers/{serverId}/monitoring/actions/install`   |
| Uninstall         | `POST /v1/api/servers/{serverId}/monitoring/actions/uninstall` |
| Host history      | `GET /v1/api/servers/{serverId}/metrics`                       |
| Service history   | `GET /v1/api/apps/{appId}/metrics`                             |
| Datastore history | `GET /v1/api/resources/{resourceId}/metrics`                   |

Installation requires `{"acknowledge": true, "retentionDays": 15}`. Retention updates require `{"retentionDays": 15}`. Management requires an Edit key with Scout configuration permission. Admins and Members can grant that permission to their personal keys. Read-only keys can inspect monitoring within their workspace.

Use the linked [REST reference](/api-reference/get_servers_by_id_metrics) for ranges, filters, and result limits. The agent ingestion endpoint is separate from the user API.

MCP provides `towbar_performance_inspect` for performance summaries and representative history points, and `towbar_monitoring_configure` for acknowledged installation, retention, or uninstall. `towbar_server_inspect` includes monitoring status. See the [MCP tool reference](/docs/api/mcp-tools) for arguments.

## Service analytics

Scout can also collect opt-in [HTTP request and website analytics](/docs/analytics) for public services. Configure analytics in the service manifest and update Scout before deploying it.

Pageview collection needs the first-party browser script. Visitor and session estimates are optional; enable them when you need bounce rate and exit pages. See [Service analytics](/docs/analytics) for setup and privacy controls.
