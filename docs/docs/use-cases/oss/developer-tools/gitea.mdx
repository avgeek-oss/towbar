The smallest Gitea installation uses its built-in SQLite database in `/data`. This recipe exposes the web interface only; Git over SSH needs a separately planned port and DNS setup.

## Towbar manifest

```yaml title=".towbar/services/gitea.service.yml"
id: gitea
name: Gitea
buildServer: null
deployment:
  type: image
  image: docker.gitea.com/gitea:1
container:
  port: 3000
  volumes:
    - name: data
      mountPath: /data
      initialData: image
environments:
  production:
    server: 192.0.2.10
rollout:
  type: recreate
  maintenanceMode: true
  reason: Persistent application data uses a single writer
secrets:
  runtime:
    - GITEA__server__ROOT_URL
domains:
  primary: gitea.example.com
tls:
  mode: direct
```

## Configure

1. Prepare the example server, connect the repository, and map `production` to the branch containing these manifests. Replace the example server IP and domain. Commit the manifests, then sync the repository and inspect the resolved configuration.
2. Set the Service's declared runtime values under **Service → Settings → Secrets** using the table below. Replace descriptions and placeholders with actual values; do not commit passwords or keys.
3. Keep the Service's named volumes attached across deployments. Towbar's Datastore backup policy does not back up Service volumes, so include them in your own recovery plan.
4. Deploy the Service, then perform the checks below before enabling auto-deploy.

## Runtime values

Save these values on the Service after the repository sync. The manifest declares required keys, not their values.

| Key                       | Value to save              |
| ------------------------- | -------------------------- |
| `GITEA__server__ROOT_URL` | https://gitea.example.com/ |

## Verify

Complete the web installer with SQLite, confirm clone links use the HTTPS domain, create a repository, and verify it remains after redeployment. Back up `/data` before upgrading Gitea.

For field constraints, see [Service manifest](/docs/services/manifest).
