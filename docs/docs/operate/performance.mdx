---
title: "Performance history"
description: "Read Scout charts, compare usage with limits, and investigate missing measurements."
---

Open a server, service, or datastore and choose **Monitor → Performance**. Scout Agent reports host and container measurements every 30 seconds when enabled. Select a time range and, for workloads, an environment and container. The URL keeps chart filters so another operator can inspect the same view.

## Read a chart

CPU and memory percentages compare observed use with the workload's declared resource limits. On the server list, CPU and memory columns instead show host capacity; a separate **% used** line appears when a Scout measurement is available. A missing sample is shown as a gap or **Not measured**, never as zero.

Use deployment, container restart, host restart, and hardware change markers to line up a change with its effect. Drag across a chart to zoom into a shorter period. Check the timestamp and timezone of a point before comparing it with deployment or incident history. A marker is a correlation aid, not proof that a deployment caused a change.

## Host restarts and hardware changes

Scout Agent reports the Linux boot ID, so a server reboot or cloud stop/start appears as **Host restart**. Restarting the Scout processes does not create a host restart. The first boot observation establishes a baseline; earlier restarts cannot be reconstructed. When the kernel boot timestamp is consistent with the surrounding observations, the marker uses that timestamp. Otherwise it uses the time Scout detected the restart.

**Machine type changed** shows the previous and new cloud instance types, for example `r8g.medium → r8g.large`. EC2 hosts with instance-type DMI metadata refresh this with each Scout collection. Other supported providers refresh their type through successful server checks. **Capacity changed** records a change in CPU count or total memory when there is no observed machine-type change. Small memory differences from kernel reservations do not produce a capacity marker.

Hardware markers use the first observation of the changed hardware, rather than a cloud-provider audit timestamp. Server metadata uses the newest observation from Scout or a successful check. Replayed and older observations cannot overwrite newer metadata. Host events also appear on service and datastore performance charts because a host change affects their running containers.

Update Scout from its settings page after upgrading Towbar to a release containing this feature. Older Scout versions continue reporting metrics. Events follow the server's performance retention period and remain available after metric rollup.

## Compare releases

For two deployment attempts, open [Deployment comparisons](/docs/deployment-comparisons). Towbar uses equal observation windows and reports data coverage alongside usage, peaks, and restarts. Low coverage makes a comparison inconclusive. Rollback changes the running image but does not undo database migrations or restore persistent files.

## Diagnose gaps and retention

The [Scout Agent](/docs/scout) page covers installation, reporting status, and server-specific retention. If data stops, inspect agent status, host connectivity, and the latest report before changing alert thresholds. Historical measurements follow the configured retention period; values outside it cannot be reconstructed from current state.

For an outage, combine the graph with [server and workload health](/docs/operate/health), [incident details](/docs/operate/incidents), and the relevant operation logs.
