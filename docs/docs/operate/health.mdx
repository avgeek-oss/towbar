---
title: "System and workload health"
description: "Check Towbar, a server, or a workload using the right observation."
---

| Scope                            | Where to check                                   |
| -------------------------------- | ------------------------------------------------ |
| Towbar control plane             | **Settings → System health**                     |
| Server connectivity and capacity | Server **Checks**                                |
| Service or datastore readiness   | Current workload state and its latest deployment |

## Check the control plane

Open **Settings → System health** and choose **Run checks**. Inspect API/database, Temporal, and worker status. Towbar checks Temporal at startup and every five minutes; old results are marked stale.

System health shows the installed release. Run [`towbar upgrade`](/docs/self-hosting/cli/install-upgrade#towbar-upgrade) on the control-plane host to update it. See [Upgrades and recovery](/docs/self-hosting/upgrades) for backups and migration requirements.

**Data Storage** and **Log Storage** show PostgreSQL and ClickHouse usage. They record readings every two hours, retain 90 days, and show missing data as gaps. See [Storage measurements](/docs/monitoring#data-and-log-storage) for permissions and scope.

If the dashboard is unavailable, run these on the Towbar host:

```bash
sudo towbar status
sudo towbar doctor
sudo towbar logs api worker temporal
```

## Check a server

Open **Checks → Check server**. Inspect SSH trust, capacity, and the latest result. A prepared server can later lose connectivity or run out of disk. For pending or failed setup, follow [Prepare a server](/docs/servers/setup).

## Check a workload

Read its current runtime state, health, and observation time. Then inspect the failing deployment stage and **Runtime Logs**, or search [retained logs](/docs/operate/centralized-logs).

For a failed health check, compare the process with `container.port` and `health` in the [manifest](/docs/services/configuration). Check the listen address, startup time, runtime secrets, and readiness response.

A successful build does not prove current health. Missing measurements do not mean zero usage. Use [Scout Agent](/docs/scout) for continuous metrics and [alert rules](/docs/scout-alerts) for incident thresholds.

## Investigate a change

Check the latest observation time, the deployment or operation result, and logs at the first failed stage. Compare the same interval in [Performance history](/docs/operate/performance); gaps indicate missing measurements. If an alert fired, open its [incident](/docs/operate/incidents) and inspect notification delivery separately from the trigger.
