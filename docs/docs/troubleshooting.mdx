title: "Troubleshooting"
description: "Find the failing stage and recover from common setup, deployment, and runtime problems."
---

Start with the last successful stage. Repository sync, deployment admission, build, promotion, and runtime health are separate operations; success in one does not prove the next completed.

Run `sudo towbar doctor` before changing installation state. It checks the host, protected configuration file, Docker, required services, installed release, database readiness, and the active local or public access path without making changes. Public mode also checks DNS, HTTPS, certificate lifetime and persistence, GitHub access, and Let's Encrypt access. It omits secret values and exits nonzero when a required check fails.

## Setup and connectivity

| Symptom                                    | Check                                            | Next action                                                                                                                                          |
| ------------------------------------------ | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Compose does not start                     | Required configuration values and migration logs | Run `sudo towbar config validate`, then inspect `sudo towbar logs migrate api`                                                                       |
| Login works locally but fails behind HTTPS | Towbar public origin                             | Check [public origins](/docs/self-hosting/environment-variables#public-origins), validate `config.yml`, and restart Towbar after changing the origin |
| Repository missing                         | GitHub App installation access                   | Grant access to the repository and approve required permissions                                                                                      |
| Repository sync fails                      | Manifest error and referenced server IPs         | Fix the reported field or register the server, then sync again                                                                                       |
| Server Setup Pending                       | SSH trust and setup result                       | Verify the host fingerprint, then complete server setup                                                                                              |

## Deployment problems

| Symptom                    | Check                                                                          | Next action                                                               |
| -------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| Push did not deploy        | Webhook delivery, sync result, auto-deploy policy, input patterns, pause state | Fix the first failed stage; use a manual deployment to isolate automation |
| Work remains queued        | Active server work and concurrency                                             | Inspect the current operation before increasing concurrency               |
| Build fails                | Dockerfile, context, build-stage secrets, host disk                            | Correct the failing command and retry                                     |
| Candidate fails health     | Port, listen address, path, startup timeout, runtime secrets                   | Make the endpoint reachable from the container network                    |
| Domain fails after build   | DNS, inbound ports, Caddy, TLS configuration                                   | Follow [Domains and TLS](/docs/domains-tls#diagnose-a-failed-route)       |
| Pre-deploy hook fails      | Hook logs and stage secrets                                                    | Resolve the command failure; promotion has not completed                  |
| New secrets are not in use | Save result and subsequent deployment                                          | Deploy after saving; save does not restart the container                  |

## Missing logs

For retained workload logs, use [Collector and storage troubleshooting](/docs/operate/log-collection#troubleshooting). **Runtime Logs** fetches current output without ClickHouse; deployment logs show build and rollout output. Check the correct view before changing collection settings.

## Preview problems

A preview requires a same-repository pull request targeting a connected environment’s mapped branch, previews enabled for that environment and the Service, and matching input paths when configured. Fork pull requests are not eligible. **Sync now** can reconcile an existing eligible pull request after a missed webhook.

If an older healthy preview remains online after a failed build, inspect the new deployment's failure. Towbar preserves the previous healthy preview until a replacement can be promoted. See [Preview environments](/docs/previews).

## Backup and restore problems

Check the relevant cloud provider integration ([AWS](/docs/integrations/aws) or [Google Cloud](/docs/integrations/gcp)), bucket permissions, object availability, engine version, and available host disk. A stale backup can still be restore-ready; a missing or incompatible object cannot. Read the final restore phase before retrying and confirm whether promotion occurred or rollback completed.

## Collect useful diagnostics

Record the Towbar version, Repository and workload IDs, operation ID, timestamps with timezone, and the last failing stage. Include a minimal manifest and redacted logs when opening a [GitHub issue](https://github.com/avgeek-oss/towbar/issues).

Do not include secret values, private keys, or database contents. Report suspected vulnerabilities through the [private security process](/docs/self-hosting/security).
