---
title: Connect the REST API
description: Scope, rotate and revoke personal and team API keys with live role restrictions.
---

REST clients connect to `https://towbar-api.example.com/v1/api` with a personal or team API key. Replace the example origin with `installation.apiBaseUrl`. API-key management and external REST access require a public HTTPS installation.

## Keys and permissions

Create personal keys in **Account Settings → API Keys**. Admins create team keys in **Team Settings → API Keys**. Enter a name, choose permissions, and choose an expiry. All three fields are required; none is selected for you. The API Keys table shows name, access, expiry and last use. The raw token is shown only when created.

| Setting                    | Options                                    |
| -------------------------- | ------------------------------------------ |
| Scope                      | Personal; Team for Admins                  |
| Access                     | Read-only; Edit for Members and Admins     |
| Administrative permissions | Admins only; includes Edit                 |
| Expiry                     | 30 days, 90 days, 1 year; Never for Admins |

Read-only grants permitted operational reads, not credential reveal. Edit adds repository, secret-update and Scout operations allowed by the current role. Administrative permissions add supported deployment and infrastructure actions. Browser-only account management, key creation and credential reveal remain unavailable to API/MCP tokens.

Personal keys intersect saved grants with current active membership. Demotion permanently narrows the key; subsequent promotion does not widen it. Removal revokes personal keys and sessions. Team keys are service identities with explicit team grants and survive their creator's departure. Missing or revoked policy records fail closed. Queued effects recheck authority before execution; revocation does not undo effects already performed.

## REST API authentication

```http
Authorization: Bearer twb_YOUR_KEY
```

Better Auth's API Key plugin generates and verifies opaque tokens. Towbar stores hashed verifiers and policy records; the token is not a JWT and contains no embedded role or credentials. Metadata and audit events never return a token or verifier. `GET /identity` identifies the current actor and team; team keys do not impersonate a human creator.

API and MCP require Bearer tokens and do not accept browser cookies. Browser sessions use cookies and origin validation. An `Origin` header must match the configured dashboard origin; CLI clients normally omit it. Use HTTPS outside local development, and keep tokens out of URLs, logs and committed files. API-key session emulation is disabled.

## Verify a connection

Set `TOWBAR_API_KEY` through your shell or secret manager, then identify the current actor and team:

```bash
curl --fail-with-body 'https://towbar-api.example.com/v1/api/identity' \
  -H "Authorization: Bearer $TOWBAR_API_KEY"
```

Check that the result identifies the intended workspace. Keep the token out of Git, URLs, and logs. Continue with the [HTTP operation reference](/api-reference/overview) or [automation workflows](/docs/api/workflows).

## MCP OAuth tokens

OAuth authorization creates a separate personal token with a fixed 30-day expiry and an MCP-only audience. MCP accepts only these OAuth tokens; personal and team API keys work only with the REST API. The **MCP Connections** page in Account Settings shows the app name, publishing domain when available, and logo. The shared consent form shows the application and lets you choose Read-only, Write, or Administrator. Any team role change revokes your MCP connections and requires new consent. See [MCP setup](/docs/api/mcp) for browser authorization, scopes, discovery, and client compatibility.

## Rotation

Create a replacement key, update the consumer, verify a permitted request, then revoke the previous key. Revocation is permanent. Key creation retries use an idempotency key and do not redisplay a previously returned token. API and MCP cannot create more keys.

## Configure rate limits

Set these in `/etc/towbar/config.yml`, then run `sudo towbar config validate` and `sudo towbar restart`:

```yaml title="/etc/towbar/config.yml"
security:
  apiRateLimit:
    max: 60
    windowSeconds: 60
```

| YAML setting                          | Default | Allowed range     |
| ------------------------------------- | ------- | ----------------- |
| `security.apiRateLimit.max`           | `60`    | 1–100000 requests |
| `security.apiRateLimit.windowSeconds` | `60`    | 1–86400 seconds   |

The fixed window starts at the first request after expiry. Each key has its own persistent limit. All REST API keys and MCP OAuth tokens from the same connection peer also share an address window. Changing keys or alternating interfaces does not create a new allowance. The browser control plane and GitHub webhook have their own authentication behavior and are not part of this bucket.

The API uses its connection peer for address limits and ignores forwarding headers. In self-hosted installations, that peer is the bundled gateway, so requests through the gateway share its address window.

The counter is updated atomically in PostgreSQL. A database outage fails requests rather than bypassing the limit. REST event streams count once when connected; subsequent reconnects count as new requests.
