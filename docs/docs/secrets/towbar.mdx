Use Towbar-managed secrets when you want to enter values directly in the dashboard. The manifest contains only variable names; Towbar stores their values separately.

## Choose when a value is used

The stage controls when Towbar supplies a value. Declare only the stages your service needs:

| Stage       | Slug         | Available to                  | Example                                               |
| ----------- | ------------ | ----------------------------- | ----------------------------------------------------- |
| Build       | `build`      | Supported image-build steps   | A package registry token used while building an image |
| Runtime     | `runtime`    | The running container         | A database URL or application API key                 |
| Pre-deploy  | `preDeploy`  | A configured pre-deploy hook  | A credential needed for a migration                   |
| Post-deploy | `postDeploy` | A configured post-deploy hook | A token used by a release notification command        |

Datastores support **runtime** secrets only. Hook values are supplied only when that hook is configured. External-service imports use runtime only; see [Secrets from external services](/docs/secrets/external).

## Declare and save a secret

Add the names a service needs to its manifest. For example, a service that only needs values while running declares `runtime`:

```yaml title=".towbar/services/api.service.yml"
secrets:
  runtime:
    - DATABASE_URL
    - API_TOKEN
```

Sync the repository. Then open **Service → Settings → Secrets**, choose the environment and Runtime stage, enter `DATABASE_URL` and `API_TOKEN`, and click **Save**. For a datastore, use **Datastore → Settings → Secrets**. Newly declared keys appear unset; they must have a value before deployment. A missing value blocks deployment, not repository sync.

Use **Form** to edit one value at a time. Stored values are masked until an authorized Admin reveals them with the eye icon; reveal a masked value before editing it. The **Editor** tab lets an Admin work with `KEY=value` lines for the selected stage. It accepts quoted values, comments, and multiline quoted strings. An unchanged value stays saved. Removing a declared key from the manifest removes its saved value on the next successful sync of that environment.

## Shared secret stores

Store a reusable value once, then reference it from each workload that needs it:

| Store              | Where to manage it                                            | Workload reference |
| ------------------ | ------------------------------------------------------------- | ------------------ |
| Workspace Secrets  | **Team Settings → Security → Workspace Secrets**              | `{{globals.KEY}}`  |
| Repository Secrets | **Repositories → repository → Settings → Repository Secrets** | `{{repo.KEY}}`     |

Choose **Build**, **Runtime**, **Pre-deploy**, or **Post-deploy** above the widget. Shared values are available across environments, including previews, within their workspace or repository. Use separate keys for credentials that must differ between environments.

Keep the required key declared in the workload manifest, then save its value as a reference in **Settings → Secrets**:

```text title="Workload Runtime secrets"
API_TOKEN="{{globals.API_TOKEN}}"
DATABASE_URL="{{repo.DATABASE_URL}}"
```

References use the **same stage** as the workload value. You can combine references with text, such as `Bearer {{globals.API_TOKEN}}`. Shared stores contain literal values and cannot reference other stores. Values are never injected automatically; a missing referenced key blocks deployment.

Repository references follow the workload's **current repository**. After a repository move, configure matching keys in the destination repository before redeploying. Existing containers keep their current values until replaced.

Members can list names and update values; only an Admin can reveal saved values. Reveals require recent authentication and are audited. REST and MCP return names and revision metadata, never plaintext. Use MCP `secrets_inspect` and `secrets_update` with `scope: "workspace"` or `scope: "repository"` and the repository's `targetId`.

## Apply changes

**Save** does not restart a container or queue a deployment. Deploy the service or datastore after saving to use the new values. Build-stage changes require a new build; runtime changes require a replacement deployment. Preview service values are isolated from persistent environments. Changing a database password in Towbar does not change the password inside an existing database, so coordinate that rotation with the database itself before redeploying consumers.
