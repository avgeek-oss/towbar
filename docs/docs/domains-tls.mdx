Towbar uses Caddy on the target server to route public HTTP traffic. Domain settings live with the service or datastore in the manifest; provider credentials come from the Towbar runtime configuration.

For [Compose projects](/docs/services/modes/compose#route-tls-per-service), declare `services.<service>.tls.mode` beside each route's `port`, `domains`, and `ingress`. Routes in one project may mix direct and Cloudflare DNS TLS. Existing Compose manifests without `tls` keep direct validation.

## Choose a TLS mode

| Mode             | DNS setup                                                                         | Credentials                                    |
| ---------------- | --------------------------------------------------------------------------------- | ---------------------------------------------- |
| `direct`         | Point public DNS at the target and allow ACME validation to reach Caddy           | No Cloudflare token                            |
| `cloudflare-dns` | Use a Cloudflare zone; Towbar manages its owned records and validates through DNS | Scoped Account API token in the Towbar runtime |

Set the primary hostname without a scheme or path. A TLS declaration requires a primary domain. A publicly routed workload also needs a container port and an HTTP health check.

## Direct TLS

Add the following fields to a service, replacing the example domain:

```yaml title=".towbar/services/web.service.yml"
domains:
  primary: app.example.com
  redirects:
    - host: www.app.example.com
      status: 301
tls:
  mode: direct
```

Point the hostname at the target server. Allow inbound HTTP and HTTPS traffic required by Caddy and certificate validation. Deploy and verify both the primary URL and each redirect.

## Cloudflare TLS

Set `integrations.cloudflare.enabled: true`, `accountId`, and `apiToken` in `/etc/towbar/config.yml`, then validate and restart Towbar. Each service or datastore selects Cloudflare DNS validation in its manifest. A deployment using `tls.mode: cloudflare-dns` is rejected if the runtime integration is missing. Towbar prepares the server's Caddy DNS module when the first such deployment runs.

Create the token under **Manage Account → Account API Tokens** in Cloudflare. Grant **Zone → Zone → Read**, **Zone → DNS → Edit**, and **Zone → Zone Settings → Read**, restricted to the zones Towbar should manage. Zone Settings Read lets Towbar verify that SSL/TLS mode is Full (strict) for proxied records. Creating account tokens requires the Super Administrator role. See [Cloudflare's account-token guide](https://developers.cloudflare.com/fundamentals/api/get-started/account-owned-tokens/).

Use a scoped account token rather than a personal or global API key. `integrations.cloudflare.zoneId` is optional when the token can discover the required zones. Towbar installs the Cloudflare DNS module on the target server when needed.

```yaml title=".towbar/services/web.service.yml"
domains:
  primary: app.example.com
tls:
  mode: cloudflare-dns
```

Cloudflare records are proxied by default. Set `tls.proxied: false` to create DNS-only address records while continuing to obtain Caddy certificates through Cloudflare DNS validation:

```yaml title=".towbar/services/web.service.yml"
domains:
  primary: ds.oss.example.com
tls:
  mode: cloudflare-dns
  proxied: false
```

DNS-only traffic reaches the server directly. Allow inbound HTTPS to Caddy; Cloudflare's proxy, caching, and WAF do not handle these requests, and DNS exposes the origin address. Caddy serves its own publicly trusted certificate, so the hostname does not need Cloudflare edge certificate coverage. Towbar still verifies origin and public HTTPS health before promotion. Full (strict) remains required for proxied routes; DNS-only routes do not use the zone's edge SSL mode.

The same setting applies to datastores with public HTTP routes and to each Compose service's `tls` block. It is supported only with `mode: cloudflare-dns`; Tunnel routes keep their own ingress policy. Existing manifests that omit `proxied` retain their current proxied behavior.

Towbar manages records it owns and completes certificate validation before promotion. Keep unrelated records and services outside that ownership boundary.

## Preview hostnames

Previews use a generated hostname beneath `preview.domain`. Direct mode needs DNS routing for those generated names, typically a wildcard. Cloudflare DNS mode manages the exact preview records and removes them during cleanup. Previews inherit the service's `tls.proxied` setting.

For proxied nested hostnames, check Cloudflare's certificate coverage as well as DNS. A resolving wildcard does not guarantee that the edge certificate covers every nested hostname.

## Cloudflare Tunnel ingress

Use `ingress.type: cloudflare-tunnel` when the workload server should not expose a public inbound application port. Create a named Cloudflare integration with a scoped account API token, account ID, optional zone ID, and Towbar's reviewed cloudflared image digest. Reference its slug and optionally a dedicated tunnel name in the Service or Compose service manifest.

Towbar creates or attaches only resources carrying its ownership identity, writes generated tunnel credentials to root-owned transient storage, starts cloudflared without a Docker socket or published administration port, and verifies the route before promotion. DNS and tunnel routes are reconciled on redeploy. Preview and removed routes are cleaned only when ownership matches; an uncertain provider response leaves a visible cleanup warning for later reconciliation.

Enabling Tunnel does not expose SSH, the Docker API, Towbar's control plane, or another service on the host. Cloudflare Access is an explicit manifest choice. Credential rotation replaces the runtime configuration on the next reconciliation.

## Move a domain to another workload

Remove the hostname from the old workload and add it to the new workload in the
same environment's manifest revision. Sync the repository, then deploy the new
owner. For example, move `example.com` from API to UI and deploy UI first.
Automatic deployment waits to update API until UI's handoff has completed.

Towbar keeps the deployed owner separate from the manifest assignment. It prepares
the target and checks its workload health before changing the route and managed
DNS ownership. On the same server, the Caddy reload removes only the transferred
hostname from the old workload's fragment; its other hostnames remain available.
Across servers, the old route stays in place until the new release commits, then
Towbar cleans up the old fragment. DNS caches can continue using the previous
address during a cross-server change.

Cloudflare ownership comments move with a verified handoff, including transitions
between address records and Tunnel CNAMEs. A target using direct TLS relinquishes
the managed comment after cutover. Stale comments from a released workload can be
reconciled using retained release provenance. You do not need to clear comments
manually for these moves.

Hostname reservations prevent concurrent deployments from taking the same domain.
An old queued deployment or rollback cannot reclaim a hostname assigned elsewhere.
If a DNS record changes after preflight, Towbar stops the deployment. Failed
preparation retains the old owner; recovery receipts restore pre-commit DNS and
routing changes without overwriting external edits. An uncertain commit or
incomplete rollback requires reconciliation before a new handoff.

Moves across environments or workspaces remain explicit conflicts while the old
route is active. Unknown external records are not adopted just because their
hostname matches. Domain handoffs are HTTP routing operations; they do not move
workload data or persistent volumes.

## Diagnose a failed route

Check these in order: domain spelling, DNS resolution, network access to the host, Caddy preparation, TLS mode and credentials, then the workload's health endpoint. A successful Repository sync or image build does not prove that the HTTPS route works.

Public health-check errors identify the hostname and HTTP status when a response arrives. If the connection fails before an HTTP response, the error retains the DNS, TLS, or connection failure detail instead of reporting status zero.

See [Troubleshooting](/docs/troubleshooting) for common failure paths.
