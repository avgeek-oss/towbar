Scout Alerts turns performance measurements into incidents you can act on. Open **Server → Monitor → Alerts** to create rules and inspect active or resolved incidents. Each server, service, or datastore page shows only its own rules and incidents in **Monitor → Alerts**. New rules automatically monitor the entity whose page you are viewing.

Use this page to configure rules. The [incident guide](/docs/operate/incidents) follows a fired condition through its graph, recovery, and notification deliveries; [performance history](/docs/operate/performance) explains the underlying measurements.

Towbar does not create alert rules automatically. The dotted 80% line in performance charts is a visual reference, not a notification threshold.

## Create a rule

1. Choose **Create rule**, enter a rule name, then choose a metric.
2. The current server, service, or datastore is selected automatically. Workload rules select **Production** or **Previews**; preview rules consider the selected workload's preview instances together.
3. Set the threshold and direction. **At least** and **At most** include the threshold itself. For metrics and public HTTP checks, choose how long the condition must remain true: 1, 2, 5, 10, 15, or 30 minutes.
4. Save the rule. It starts active, and all configured notification destinations receive alerts and recoveries automatically.

A server without notification destinations still creates incidents in Towbar. Adding a destination does not send an immediate test; a firing incident becomes eligible on the next evaluation. Admins and Members can create, change, pause, resume, or delete rules. Viewers can inspect them.

| Example rule            | Trigger                              | Recovery                            |
| ----------------------- | ------------------------------------ | ----------------------------------- |
| Disk nearly full        | Root disk at least 90%               | Disk falls below 90%                |
| High memory usage       | Memory at least 90%                  | Memory falls below 90%              |
| High CPU usage          | CPU at least 90%                     | CPU falls below 90%                 |
| Container restart loop  | At least 3 restarts within 5 minutes | Fewer than 3 restarts in the window |
| Scout stopped reporting | No report collected for 3 minutes    | Reports resume                      |

Metric and HTTP rules created in the dashboard default to a one-minute duration. A breach must remain continuous for the selected duration; missing or stale readings cannot complete it. Older rules without a duration fire on the first qualifying reading until edited. Restart rules count events in a 1-to-60-minute window; missing-report rules use their report-age threshold. Recovery follows the first fresh measurement that clears the trigger.

Use **Pause** and **Resume** to control evaluation. Paused rules still count toward these limits:

| Scope                            | Limit                                                    |
| -------------------------------- | -------------------------------------------------------- |
| Server, Service, or Datastore    | 10 rules per entity, shared by production and previews   |
| One server and all its workloads | 100 rules total, including at most 10 public HTTP checks |

## Inspect an incident

Open **Monitor → Incidents** for workspace history, or select **View Incident** beside a rule. The drawer separates the trigger and its readings from notification delivery. A queued message is not a successful delivery.

Use the Monitoring tab to compare the metric with its threshold. Dotted spans mark missing measurements. History follows the server's retention setting; restart and traffic windows are available for the last 24 hours. See [Investigate incidents](/docs/operate/incidents) for recovery, closure reasons, and delivery checks.

## Measurements and incident states

Host and workload gauges use the reported metric units. The editor presents bytes as GiB and throughput as MiB/s; REST thresholds use bytes and bytes per second. For multiple instances, a gauge rule evaluates the worst instance reading rather than adding utilization percentages. Restart rules count increments within each container identity, not a new container's initial counter or a counter reset.

**Healthy** means the latest evaluation does not meet the trigger condition, or an active incident has cleared. **Alerting** means the condition is active. **No recent data** cannot prove recovery: missing measurements are not treated as zero. **Scout inactive** means collection is intentionally disabled or the workload is no longer assigned to the server.

Metric rules require Scout Agent to be enabled. Missing-report rules include an installation grace period and do not alert on intentional uninstall. Public HTTP checks are performed by the control plane and do not require an installed agent.

Deleting or pausing a rule, changing its condition, or removing its monitored workload closes its incident with an explicit reason. That is different from recovery and does not send a recovery notification. Active incidents remain visible; resolved incidents follow the server's Scout retention setting, defaulting to 15 days when no agent is installed.

## Traffic count alerts

Services with [analytics](/docs/analytics) enabled can use **HTTP requests** as an alert metric. **Pageviews** is also available when pageview collection is enabled. These metrics count production traffic across all paths, after the service’s analytics exclusions. They are not available for servers or datastores.

Choose **At least** or **At most**, a whole-number threshold, and **Count within (minutes)** from 1 to 60. For example, alert when HTTP requests reach 10,000 in five minutes, or when pageviews are at most zero in ten minutes. Counts use a rolling window, evaluated as Scout reports arrive; there is no additional duration or average/peak setting. Pageviews count received browser events, so the pageview script must be installed.

Scout needs a full window of consecutive, ready collection reports before it can evaluate the rule. Zero traffic is a valid count. Missing, stale, dropped, or incomplete collection data instead produces **No recent data** and cannot open or recover an incident. Older agents must be updated to report collection readiness. Disabling the corresponding analytics collection closes active incidents without sending recovery notifications. Traffic incident charts show up to the last 24 hours.

## Public HTTP checks

Choose **Public HTTP endpoint** as a server rule's metric. Set a public HTTP or HTTPS URL, request method, expected status range, interval, and timeout. Only use endpoints that are safe to request repeatedly.

- **GET** or **HEAD**, every 30 to 300 seconds in 30-second increments.
- A total timeout from 1 to 10 seconds, including DNS resolution and redirects.
- A healthy HTTP status range, defaulting to 200–299.
- Zero to three redirects; redirects are not followed by default.
- Unavailable results must continue for the selected duration before opening an incident. Recovery follows the first successful check.

An unexpected status, timeout, DNS/connection failure, or invalid TLS certificate counts as unavailable. A blocked destination is shown as a check error and cannot establish recovery. Each redirect is resolved and validated separately. Private, loopback, link-local, reserved, and metadata-service addresses are blocked, including mixed public/private DNS answers. Connections are pinned to the validated address. Only ports 80 and 443 are accepted; custom headers, credentials, cookies, and request bodies are not supported. Response bodies are not buffered or retained.

These checks measure availability **from your Towbar control plane**. They are not a geographically distributed uptime service and cannot detect an outage of the control plane itself. Keep an independent external check for Towbar if you need that coverage.

## Notification destinations

Configure provider credentials under `notifications` in `/etc/towbar/config.yml` and run `sudo towbar restart`. Then select destination categories in the dashboard. See [notifications](/docs/integrations/notifications) for the schema. Server and workload alerts use the matching routes.

Incident routes follow workspace subscriptions and any workload-specific destinations declared in Git. There are no per-rule channel selections. The incident remains visible even if no destination is configured or delivery fails.

Towbar sends one firing notification per incident. Recovery messages go only to destinations that received the firing notification. Pausing or changing a rule suppresses queued messages that no longer apply; a message already being sent may still arrive. See [notification delivery history](/docs/integrations/notifications#delivery-history) for retries and provider failures.

## API and MCP

All routes below are relative to `/v1/api` and use [API key authentication](/docs/api/authentication). Reads accept Read-only or Edit keys. Mutations require an Edit key with alert configuration permission; personal keys must belong to an Admin or Member. Provider credentials and notification routes cannot be changed through the API.

| Task                                    | Route                                                    |
| --------------------------------------- | -------------------------------------------------------- |
| Rules, evaluations, and destination IDs | `GET /servers/{serverId}/scout-alerts`                   |
| Create rule                             | `POST /servers/{serverId}/scout-alerts/rules`            |
| Replace rule settings                   | `PUT /servers/{serverId}/scout-alerts/rules/{ruleId}`    |
| Delete rule                             | `DELETE /servers/{serverId}/scout-alerts/rules/{ruleId}` |
| Incident history                        | `GET /servers/{serverId}/scout-alerts/incidents`         |

Rule inspection also accepts `deployableId` to filter before the result limit: use a workload UUID or `server`. Omitting it returns rules across the server and its workloads for API discovery.

Incident history accepts `state=active|resolved|all`, an optional `deployableId` (a workload UUID, or `server` for server-only incidents), and `limit` up to 50. Pass both `nextBefore` and `nextBeforeId` as `before` and `beforeId` for the next page.

MCP provides `towbar_alerts_inspect`, `towbar_alerts_configure`, and `towbar_alerts_remove`. Discover IDs before mutation, inspect the current rule before replacing it, and preserve settings the user did not request changing. See the [tool reference](/mcp-reference/overview) and the Scout Alerts API section for full schemas.
