The server **Overview** shows the latest observed capacity and health. Use **Check server** for a fresh reading; a recorded CPU or memory value is not a guarantee that the host is reachable now. Cloud instance detection uses local metadata and is best effort.

## Capacity and build concurrency

Set `buildConcurrency` under **Settings → Configuration** to limit simultaneous build work. `previewBuildConcurrency` reserves a bounded share for previews, defaults to 1, cannot exceed the total, and is capped at 4. Production and maintenance work take priority. Increasing concurrency uses real CPU, memory, and disk bandwidth; compare the configured limit with recent [Scout Agent](/docs/scout) measurements.

## Terminal

Admins can choose **Terminal → Connect** after configuring a verified SSH key. The shell runs as the configured SSH user and can change the host outside Towbar's deployment scheduler. A recent sign-in is required; API keys and MCP cannot open a terminal. Towbar audits connection open and close events, but does not store terminal input or output. Use it for inspection and deliberate maintenance, and prefer tracked deployment or resource operations for workload changes.

## Clean up leftover workloads

Open **Settings → Docker cleanup** to review unused objects from the latest server check. Select **Request Cleanup** to queue a fresh server-level attempt. Cleanup discovers current Towbar-owned objects when it starts; it does not rely on the table's older snapshot. An empty Docker inventory does not mean that removed workloads have no routes or configuration left to retire. Results identify routes, networks, and workload retirement separately from containers, images, and volumes.

Removing a manifest in Git marks the workload for retirement and preserves its runtime and storage. Ordinary Docker cleanup protects these pending retirements, conflicts and active workloads.

An administrator can explicitly remove a retirement under [Conflicts and retirements](/docs/repositories/conflicts-and-retirements). Towbar queues a scoped cleanup on every associated runtime and build server. It removes only that workload's owned containers, persistent volumes, configuration and routes. **Deleting volumes permanently deletes their data.** History and backups remain.

Each attempt rechecks ownership and active operations. Sync and new deployment admission wait while server cleanup is running. Cleanup preserves other workloads, shared networks and external objects, and never runs an unrestricted Docker prune.

Use **View result** to inspect removed, skipped and failed objects. Failed permanent removal keeps its ID reserved. Retry from Retirements after fixing the reported issue. A missing or disconnected historical server must be registered again before removal can be queued.

For removal of the server itself, read [Remove a server](/docs/servers/remove).

### Caddy recovery during cleanup

Route cleanup validates the staged configuration before applying it. If Caddy is running, Towbar reloads it once for all removed routes. If an earlier cleanup exhausted systemd's start limit and left Caddy failed with `start-limit-hit`, Towbar resets that limit and starts the validated configuration once. A deliberately stopped service is not started automatically; start Caddy before retrying cleanup.

If validation, recovery, or reload fails, Towbar restores the staged route files and retains the workload configuration and domain ownership for retry. Old failed attempts remain in history after a successful retry.
