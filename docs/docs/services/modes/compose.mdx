---
title: "Compose project"
description: "Deploy a multi-service project from repository-owned Compose files."
---

Choose a Compose workload when several services must be deployed as one project. Place its entity under `.towbar/services` and point `file` and optional `overrides` at Compose files in the same immutable checkout.

## Example manifest

This is the validated example from the Towbar `examples/platform-modes` project. Replace the documentation IP, domain, and image choices with values for your environment.

```yaml title=".towbar/services/storefront.compose.yml"
id: compose-example
name: Compose example
file: examples/platform-modes/compose/compose.yml
overrides:
  - examples/platform-modes/compose/compose.production.yml
profiles: [production]
strategy: maintenance
services:
  web:
    port: 3000
    domains: [compose.example.com]
    ingress:
      type: proxy
    tls:
      mode: direct
  cache: {}
environments:
  production:
    server: 192.0.2.10
```

## Configure it

The example gives the `web` service a public proxy route and keeps `cache` internal. Towbar validates the resolved Compose project before Docker opens it. Compose builds run on the runtime server because the service graph is resolved as one project.

Remote includes, privileged containers, Docker socket mounts, host bind mounts, devices, public host ports, and external or explicitly named Docker resources are rejected. Compose replacement uses `recreate` or `maintenance`; rolling replacement is not supported.

Map the named environment to a branch, register and prepare its server, then sync the repository. Start with a manual deployment and verify the running service before opting into automation. See [Service manifest](/docs/services/manifest) for shared fields and [Deployment modes](/docs/platform-deployments) to compare modes.

## Track source changes

Compose tracks the complete Git repository tree by default, including dotfiles.
Changes to referenced configs, included Compose files, Dockerfiles, build contexts,
or shared dependencies therefore change the deployment digest. Added, removed,
renamed, and executable-mode changes participate too. A commit with identical
tracked files keeps the same digest.

Set `autoDeploy: true` to deploy changed inputs after a successful sync. Omitting
it or setting `false` keeps deployments manual while retaining full-tree tracking.
For a monorepo, scope automatic deployment to additive, repository-relative globs:

```yaml title=".towbar/services/observability.compose.yml"
id: observability
name: Observability
file: observability/compose.yml
overrides:
  - observability/compose.production.yml
autoDeploy:
  inputs:
    - observability/**
    - shared/collector-config/**
    - shared/docker/**
strategy: maintenance
environments:
  production:
    server: 192.0.2.10
```

The primary Compose file and explicit overrides always participate, even outside
the declared scope. Cover every other referenced file, build context, include,
and shared dependency in `inputs`; Towbar does not discover those dependencies
automatically. Paths are relative to the repository root. Exclusion patterns,
absolute paths, and parent traversal are rejected. A scope that matches no tracked
files is rejected even when the mandatory Compose files exist. Use the environment override
or Repository automation controls to pause automatic deployment.

Sync requires a complete repository tree and regular primary/override files at
the selected revision. A queued deployment retains its configuration and digests;
later syncs cannot change that release's inputs. After upgrading from the older
Compose-file-only tracking, the next sync can queue one additional deployment for
an opted-in workload while establishing the broader digest baseline. Rollback
keeps the retained release's original snapshot.

Shared input groups can be declared in `towbar.yml` and referenced by either
Services or Compose workloads:

```yaml title="towbar.yml"
version: 2
deploymentInputs:
  shared-platform:
    - shared/config/**
    - shared/docker/**
environments:
  production: {}
```

Use `inputs: [observability/**, $shared-platform]` in the workload's `autoDeploy`
configuration. Groups contain additive repository globs; nested group references
are rejected.

## Route TLS per service

Each public service chooses its own `tls.mode` alongside `port`, `domains`, and `ingress`. Omitting `tls` keeps direct Caddy certificate validation. Choose `cloudflare-dns` to reconcile Cloudflare address records and obtain certificates through the configured runtime integration. Cloudflare records are proxied by default; set `tls.proxied: false` on a service for DNS-only routing. Proxy ingress still requires HTTPS access to the server; DNS validation does not create a Tunnel.

```yaml title=".towbar/services/platform.compose.yml"
id: platform
name: Platform
file: compose.yml
services:
  api:
    port: 3000
    domains: [api.example.com]
    ingress:
      type: proxy
    tls:
      mode: cloudflare-dns
  console:
    port: 8080
    domains: [console.example.com]
    tls:
      mode: cloudflare-dns
  web:
    port: 80
    domains: [web.example.com]
    tls:
      mode: direct
environments:
  production:
    server: 192.0.2.10
```

Configure the token, zone permissions, and Full (strict) mode described in [Domains and TLS](/docs/domains-tls#cloudflare-tls). TLS requires at least one domain and a service port. A `cloudflare-tunnel` route must omit `tls`; Cloudflare manages its public certificate.

Compose waits for service health and validates the Caddy configuration before recording a release. Verify each HTTPS hostname after deployment.

Towbar refuses conflicting or foreign address records. An unmanaged address record may be adopted only when its type and target IP already match. Before release commit, a failed route rolls back DNS writes that still match the records Towbar changed and restores the previous Compose project. After commit, cleanup removes only obsolete owned address records, preserving current domains and unrelated records. Provider uncertainty leaves an error or cleanup warning for operator review. Compose rollback uses the retained source and route policies; it does not reverse changes to persistent volumes.

When a route switches from `cloudflare-dns` to direct TLS, Towbar preserves its address record and clears the ownership comment after release commit. Manage that record manually from then on, including removing it if the route is removed.
