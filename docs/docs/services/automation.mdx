title: "Automation and previews"
description: "Opt a Service into automatic deployment, PR previews, notification routing, and scanning."
---

Repository sync does not by itself deploy a service. Opt in with `autoDeploy`, then list the repository paths that can change the built result:

```yaml title=".towbar/services/web.service.yml"
id: web
name: Web
autoDeploy:
  inputs:
    - package.json
    - pnpm-lock.yaml
    - apps/web/**
```

Include shared libraries, lockfiles, build scripts, and Dockerfiles as needed. The Repository's automation control can pause automatic work during maintenance. A manual **Deploy** remains a separate action. Start with one manual deployment and verify the running service before enabling automation.

Compose workloads accept the same `autoDeploy.inputs` form. Without an explicit
scope they track the full repository tree; with one they always retain the primary
Compose file and explicit overrides. Include every referenced config and build
dependency in a scoped declaration. See [Compose change tracking](/docs/services/modes/compose#track-source-changes).

## Pull request previews

Enable previews for an environment in `towbar.yml`, then opt the Service in with a base domain:

<CodeGroup>

```yaml title="towbar.yml"
version: 2
environments:
  staging:
    previews:
      enabled: true
```

```yaml title=".towbar/services/web.service.yml"
domains:
  primary: staging.example.com
tls:
  mode: direct
preview:
  enabled: true
  domain: preview.example.com
  ttlHours: 72
environments:
  staging:
    server: 192.0.2.11
```

</CodeGroup>

The Service block is a fragment to merge into its existing declaration. Eligible GitHub pull requests target the branch mapped to `staging`. Preview secrets are isolated from persistent environment values; datastores do not create previews. Read [Preview environments](/docs/previews) for expiry and cleanup.

## Other automation

Use `notifications` to route a Service's events to additional workspace-configured destinations. It takes effect after a successful environment sync without a deployment. `vulnerabilityScanning` controls image scanning, while `jobs` runs scheduled commands from the deployed image. Follow [Notifications](/docs/integrations/notifications), [Vulnerability scanning](/docs/vulnerability-scanning), and [Scheduled jobs](/docs/services/jobs) for their separate configuration and execution rules.
