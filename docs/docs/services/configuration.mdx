The `container` block describes how the deployed image runs. `port` is the port **inside** the container; the process must listen on the container's network interface. Set resource limits near the port so a reviewer can assess expected capacity:

```yaml title=".towbar/services/web.service.yml"
container:
  port: 3000
  resources:
    cpus: 1
    memory: 1g
health:
  path: /health
  timeoutSeconds: 60
```

The HTTP health path should respond without interactive authentication. A successful build is not sufficient for traffic promotion: Towbar waits for the candidate to pass readiness. Allow enough time for startup, but investigate a consistently slow start rather than raising the timeout indefinitely.

## Private connectivity

Set the same `container.network` on a Service and Datastore on the same server. A Datastore's ID is its network alias unless it sets `networkAlias`:

```yaml title=".towbar/services/web.service.yml"
container:
  port: 3000
  network: application
```

For a PostgreSQL datastore with alias `postgres`, the Service can connect to `postgres:5432`. Put the credential-bearing URL in a [service runtime secret](/docs/secrets), not in the manifest. A Docker network on one host does not connect containers across different servers.

## Persistent storage

Use a Docker-managed named volume when a process must retain files across replacement:

```yaml title=".towbar/services/files.service.yml"
rollout:
  type: recreate
  maintenanceMode: true
  reason: The service uses a single-writer volume
container:
  port: 3000
  volumes:
    - name: uploads
      mountPath: /app/uploads
      initialData: image
```

Create the mount directory in the image with ownership for its runtime user. Volumes survive redeployments and image rollback, remain on their server, and are not backed up by Towbar. `initialData` applies only when adding a new volume: `previous-container` imports from the stopped container, while `image` initializes from the new image. Environment overrides replace the common volume list. Host-directory bind mounts are not accepted; keep backups of important files outside Towbar.

Removing the Service from Git and successfully syncing its environment queues server cleanup, including permanent deletion of its exclusively owned volumes. Re-adding it after cleanup creates fresh storage. Back up required data first; see [sync removal](/docs/repositories/sync) and [cleanup history](/docs/servers/operations).

## Docker host logs

For retained custom collector integrations, a trusted Service can request one fixed, read-only host mount. An Admin must explicitly set `hostLogCollection: true` through the server configuration API or MCP, then declare `container.hostLogs.dockerJsonFiles: true`. Towbar’s [native log collector](/docs/operate/centralized-logs) does not require this custom-Service permission.

```yaml title=".towbar/services/host-logs.service.yml"
id: host-logs
name: Host logs
deployment:
  type: dockerfile
  context: observability/fluent-bit
  dockerfile: observability/fluent-bit/Dockerfile
rollout:
  type: recreate
  maintenanceMode: true
  reason: One collector writes the persistent cursor and buffer
container:
  port: 2020
  resources:
    cpus: 0.25
    memory: 256m
  hostLogs:
    dockerJsonFiles: true
  volumes:
    - name: state
      mountPath: /var/lib/fluent-bit
      initialData: image
health:
  path: /api/v1/health
  timeoutSeconds: 60
environments:
  production:
    server: 192.0.2.10
```

Towbar reads `DockerRootDir` from the target daemon and mounts its `containers` directory at `/var/lib/docker/containers`. A custom Docker data directory is supported. The manifest cannot choose a host path, make this mount writable, or attach a Docker socket. Named volumes must not overlap the log mount. Compose workloads, deployment hooks, and scheduled jobs do not receive this capability, and collectors cannot enable Previews.

<Warning>
  This mount exposes logs and container metadata for every container on the
  server, including workloads outside the collector's Repository. Those files
  can contain credentials and private data. Only deploy collector images and
  configuration you trust with that access.
</Warning>

The collector runs as UID/GID `0:0` with all Linux capabilities dropped, `no-new-privileges`, a read-only root filesystem, and a 16 MiB temporary `/tmp`. This requires rootful Docker without user namespace remapping. Towbar creates an owned `local` driver volume with fixed `bind,ro,private` options, checks its source and ownership before startup, and mounts it read-only with private propagation. Existing and future host submounts are excluded. The CPU and memory limits and persistent named storage are required; the example's 0.25 CPU and 256 MiB are a starting budget. Measure consumption and set a bounded on-disk buffer in the collector configuration. Collector runtime secrets cannot override Docker connection settings such as `DOCKER_HOST` or `DOCKER_CONTEXT`.

For Fluent Bit, tail `/var/lib/docker/containers/*/*-json.log`, keep the Tail database and filesystem buffer under `/var/lib/fluent-bit`, and enable its HTTP server and health check on `0.0.0.0:2020`. See the [Tail input](https://docs.fluentbit.io/manual/data-pipeline/inputs/tail), [buffering](https://docs.fluentbit.io/manual/administration/buffering-and-storage), and [health check](https://docs.fluentbit.io/manual/administration/monitoring#health-check-for-fluent-bit) configuration. Towbar preserves the volume across replacement and requires a maintenance rollout so two collector versions cannot write it together.

Towbar uses Docker's `local` logging driver for the collector itself, with rotation capped at three 10 MiB files. Its output is therefore excluded from the `*-json.log` glob without a container-ID exclusion rule. Other containers must use `json-file` to appear in that glob; this capability does not collect journald, `local`, or remote-driver logs.

API keys need edit access with administrative operations enabled and explicit `deployment.create` and `server.collectLogs` grants. Towbar checks authority at admission and again when a queued deployment starts, including rollback to a retained collector image. It also checks the server's current opt-in. Disabling the setting prevents further collector deployments; stop and remove existing collector containers to revoke their mounted access. Changing the setting does not unmount or stop a running container.

Resuming a paused collector rechecks the successful sync's captured actor and its current access. A blocked collector is skipped with a reason while other automatic deployments and Preview reconciliation continue. Server consent changes preserve workload deployment digests. Rollback restores the target release's collector mode, resource limits, state volumes, and maintenance rollout.

After removing `hostLogs`, deployment cleanup reclaims the owned host-log bind volume once every container reference is gone, including stopped containers. Server orphan cleanup can also reclaim an unused host-log volume for an active Service. Persistent cursor and buffer volumes remain intact. Re-enabling collection recreates the bind from the daemon's current data-root; a changed data-root can replace a stale owned bind only after its container references have been removed.

## Runtime commands and repository files

Services and managed Datastores accept `container.command` as an argument array
and `container.entrypoint` as one executable path. Command arguments replace
the image CMD and are passed to its entrypoint. An entrypoint override selects a
different executable; put its arguments in `command`. An empty entrypoint
clears the image entrypoint. Omit both fields to retain existing image and
managed engine defaults.

Declare each non-secret configuration file explicitly:

```yaml
rollout:
  type: recreate
  maintenanceMode: false
  reason: Readiness uses a separate port
container:
  port: 4318
  entrypoint: /bin/sh
  command: [-ec, "exec collector --config=/etc/collector.yml"]
  configFiles:
    - source: config/collector.yml
      mountPath: /etc/collector.yml
    - source: config/tool
      mountPath: /app/bin/tool
      mode: "0555"
health:
  path: /
  port: 13133
  publicPath: /status
```

`source` is a canonical repository-relative regular file, taken from the same
immutable commit as the deployment. Directories, traversal, and symlinks are
rejected. `mountPath` is an absolute container file path. File targets cannot
overlap each other or cover a volume; a file may overlay a location inside a
named data volume. Up to 50 files, 16 MiB per file and 64 MiB in total are
supported. Files mount read-only with mode `0444`, or `0555` for an executable.
Their parent directories are traversable by non-root image users. This API
does not accept arbitrary host paths or runtime/socket mounts.

Declared files are included in source-input and runtime configuration digests,
even when a Service's auto-deploy inputs select other paths. Sync requires a
complete repository tree containing every file. Secret values stay in Towbar's
existing runtime and hook secret bundles. Prefer the image's environment
substitution support for credentials; Towbar does not template secrets into
these source files.

Towbar retains a checksum receipt and each release's files on the target server.
Rollback verifies those retained bytes and modes and reuses them without needing
repository access. Missing or altered files fail rollback before replacement.
Retained configuration directories are not automatically garbage-collected in
this version. Keep them while their releases remain usable. Managed backup
capture remains available; automated datastore restore currently rejects
configuration files or entrypoint overrides, so use engine-native recovery for
those configurations. Deployment rollback still restores the prior runtime and
its configuration without reversing data changes.

## Readiness and public probes

The default Service health check remains HTTP `/api/health` on
`container.port`. An HTTP check may declare `health.port` to probe another
container port; Towbar publishes that port only on target loopback. Routing
continues to use `container.port`. Use `health.type: command` with a `command`
array for a command executed inside the candidate, or `health.type: container`
for image-provided Docker health (running state when the image has no check).
These options require a `recreate` rollout. Rolling deployment continues to
require HTTP readiness on the service port.

When public routing uses a different endpoint or readiness uses a command,
declare `health.publicPath` for a successful HTTP probe through ingress. It is
required with a public domain when readiness uses a separate port or a
non-HTTP check. Public TLS and routing checks remain independent of private
readiness; the readiness port is not routed publicly.

## Initialization with the selected image

A deployment hook may override its image entrypoint. Hook containers receive
the selected image, declared network, read-only configuration files, resource
limits, and their own secret bundle. For an ordered initialization sequence:

```yaml
hooks:
  preDeploy:
    entrypoint: /bin/sh
    command:
      [
        -ec,
        "migrate ready && migrate bootstrap && migrate sync up && migrate async up",
      ]
    timeoutSeconds: 900
```

The hook exits on failure and must finish before startup. Hooks are skipped for
rollback; keep an application-specific migration-status check in the startup
command when needed. Independent deployables have no cross-workload ordering;
deploy required dependencies first and wait for their health. See the
[independent OCI example](https://github.com/avgeek-oss/towbar/tree/main/examples/independent-oci)
for a five-entity validation case.
