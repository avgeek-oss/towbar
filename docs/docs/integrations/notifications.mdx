Towbar records provider-neutral events and sends each matching event to its subscribed destinations. Credentials live in `/etc/towbar/config.yml`. Email recipients, Slack channels, and Telegram chats are managed in **Manage → Notifications**. Discord webhook pairs and webhook push endpoints live in YAML; their event subscriptions are selected in the dashboard. The provider list remains visible even when a runtime connection is missing.

| Provider     | What you configure                                | Setup guide                                              |
| ------------ | ------------------------------------------------- | -------------------------------------------------------- |
| Email        | SMTP connection and recipient addresses           | [Email (SMTP)](/docs/integrations/notifications/email)   |
| Slack        | Bot token and channel IDs                         | [Slack](/docs/integrations/notifications/slack)          |
| Discord      | Webhook ID and token pairs                        | [Discord](/docs/integrations/notifications/discord)      |
| Telegram     | Bot token, chat IDs, and optional topics          | [Telegram](/docs/integrations/notifications/telegram)    |
| Webhook push | HTTPS URLs, optional headers, and signing secrets | [Webhook push](/docs/integrations/notifications/webhook) |

## Decide who receives an event

Workspace destinations receive matching events from all services and datastores. A service or datastore manifest can add read-only Email, Slack, Discord, or Telegram destinations for that entity. Webhook push remains workspace-only.

### Route events for one workload

Add destinations under `notifications` in a Service or Datastore manifest. For example:

```yaml title=".towbar/services/web.service.yml"
notifications:
  email:
    - address: web-ops@example.com
      deployments: true
      deploymentFailures: false
      backupsAndRestores: false
      alertsAndIncidents: true
  slack:
    - channelId: C12345678
      deployments: false
      deploymentFailures: true
      backupsAndRestores: false
      alertsAndIncidents: true
```

Each destination must enable at least one category. These subscriptions take effect after a successful environment sync; no deployment is needed. Keep provider credentials in `/etc/towbar/config.yml`. The workload's **Monitor → Notifications** page shows synced destinations and subscriptions without edit controls.

For deployments, choose **All** to receive every deployment and preview event or **Failures only** to receive `deployment.failed` and `preview.failed`. Workspace destinations offer one choice at a time; clear the selection to turn deployment notifications off. In manifests, set `deploymentFailures: true` for failures only. If both `deployments` and `deploymentFailures` are true, **All** takes precedence. **Backup & Restore** and **Incidents** are independent subscriptions. Service health and Scout events follow Incidents. New runtime-managed Discord and webhook destinations start with no subscriptions, so select at least one category before expecting routine events.

## Apply runtime changes

Set `notifications.enabled: true` and add the relevant provider under `notifications.providers`. Run `sudo towbar config validate` and `sudo towbar restart`. Invalid YAML, duplicate IDs, missing credentials, or unsafe destinations fail validation. The [runtime configuration reference](/docs/self-hosting/configuration#notifications) lists the common shape; each provider guide has a focused example.

## Delivery history

Open **Manage → Notifications → Health → Deliveries** to filter persisted attempts by provider, category, or entity. The list includes workspace and manifest destinations. Inspect an attempt's status, timestamps, safe provider error, and retries before changing a route. A succeeded delivery means the provider accepted it; it does not prove a recipient read it.

Towbar resolves credentials when a delivery runs, retries transient failures with bounded backoff, and keeps history after a destination is removed. Authentication failures call for correcting YAML and restarting; a wrong subscription calls for changing the destination's category in the dashboard. Repeated rate limits pause the affected destination rather than blocking the underlying service or datastore operation.

Delivery history can be filtered by state, provider, category, entity, and search text. Its URL preserves the filters and current page, so a failed-delivery investigation can be bookmarked or shared.
