Create a Google Cloud project and a Cloud Storage bucket for recovery points. Give a dedicated service account access to list, create, read, and remove the objects Towbar owns in the intended bucket. If the bucket uses a customer-managed encryption key, grant its [Cloud Storage service agent access to that key](https://docs.cloud.google.com/storage/docs/encryption/using-customer-managed-keys). Export a JSON key for that account, encode the complete file as Base64, and add it to `/etc/towbar/config.yml`:

```yaml title="/etc/towbar/config.yml"
integrations:
  gcs:
    enabled: true
    projectId: example-project
    bucket: example-backups
    prefix: towbar
    serviceAccountJsonBase64: <base64-encoded-json>
```

For example, `base64 < service-account.json | tr -d '\n'` produces a single-line value. Run `sudo towbar config validate` and `sudo towbar restart`. Google Cloud Storage appears under **Manage → Integrations → Backup providers** only when the local configuration is valid; Towbar never returns the service-account JSON.

## Verify recovery

Set a managed datastore's [backup policy](/docs/backups) to use `gcs`, create a recovery point, and check the stored object's verification result. Perform a [fresh-target restore](/docs/restores) to confirm read and compatibility permissions. If a run fails, check project ID, bucket and prefix, service-account scope, object availability, and the bucket's encryption policy. Rotate by updating `config.yml`, restarting Towbar, verifying a backup and restore path, and then revoking the old key.
